# Building an E2E Accessibility Testing Integration with Playwright and @axe-core/playwright

## Executive summary

End-to-end (E2E) accessibility automation with Playwright and `@axe-core/playwright` works by **driving the real browser UI** to specific application states and then **injecting and running axe-core inside the page context** to produce a **JSON accessibility findings object** (violations, passes, incomplete, inapplicable). citeturn7view0turn1view0turn2view0turn5view0

Two implementation details matter for “WCAG 2.2 tags and AAA rules”:

- In axe-core, `axe.run()` **runs all enabled rules** by default (not experimental ones). citeturn5view0  
- Several rules you care about for stricter conformance are **disabled by default**, including:
  - **WCAG 2.2 A/AA automated rules** (currently documented as disabled by default in axe-core; e.g., `target-size`). citeturn6view0  
  - **WCAG 2.x AAA automated rules** (e.g., `color-contrast-enhanced`, `identical-links-same-purpose`, `meta-refresh-no-exceptions`)—also documented as disabled by default. citeturn6view0  

Therefore, to “include WCAG 2.2 tag or AAA rules” in a Playwright+axe integration, you typically need **both**:
1) **Rule selection (tags / runOnly)**, and  
2) **Explicit enabling of the disabled-by-default rule IDs** via `axe.run` options (through `AxeBuilder.options(...)`). citeturn5view0turn6view0turn1view0

This report provides: a technical explanation of how automated accessibility scanners work, a step-by-step integration guide (local + CI + reporting), explicit code examples for WCAG 2.2/AAA selection and overrides, diagrams (Mermaid flow + ER), a prototype schema, sample JSON output mapping to WCAG tags, and best practices (performance + security + privacy). citeturn7view0turn8view0turn15view0turn2view0turn6view0

## How automated accessibility tools work technically

Automated accessibility testing tools generally implement a **rule engine** that inspects the rendered page’s structure and semantics, compares them against machine-testable requirements, and returns structured results (usually JSON). In the axe ecosystem, axe-core is the engine; it is open source and designed to integrate into existing test environments. citeturn14search11turn0search10

### Core execution model in axe-core

At a high level, axe-core’s API usage flow is:

1) Load the page,  
2) Optionally configure axe,  
3) Run `axe.run(...)`,  
4) Assert or store results,  
5) Repeat for other app states/pages. citeturn2view0

In rule-engine terms, axe-core rules are defined as JSON-like rule descriptors that:
- **Select** which elements to test (via a CSS selector and optional match filters),
- Then run one or more **checks** per rule, producing pass/fail/incomplete outcomes. citeturn16view0

Important built-in constraints:
- **Hidden elements are ignored by default** (rules typically exclude hidden elements unless configured otherwise). citeturn16view0  
- Axe results can be **“incomplete / needs review”** when the engine cannot produce a definitive automated conclusion. citeturn16view0turn2view0  

### What the scanner inspects (detection methods)

Below is a practical “text document” explanation of the main detection methods you asked for, grounded in how browsers and axe operate.

**DOM analysis (structure + semantics).**  
Browsers build a DOM tree from markup, and accessibility tools can traverse it to verify structural requirements: headings, landmarks, labels, link/button semantics, duplicate IDs, etc. Playwright’s own accessibility testing guide calls out examples like poor contrast, missing labels, and duplicate IDs as issues automation can catch. citeturn7view0

**ARIA checks (role/name/value integrity).**  
Browsers build an **accessibility tree** derived from the DOM and related semantics; that tree is exposed through platform accessibility APIs to assistive technologies. citeturn12search0turn12search6turn12search17  
ARIA exists to supplement native HTML semantics so custom widgets and dynamic behaviours can be conveyed to assistive tech. citeturn12search2turn12search4  
Many automated checks validate ARIA usage patterns (valid role/attribute combinations, required naming, etc.) because those are deterministically inferable from attributes and computed semantics. citeturn7view0turn16view0

**Accessible name computation (labels users actually hear).**  
A major subset of accessibility defects is “missing or incorrect accessible names”. The W3C Accessible Name and Description Computation spec defines how user agents compute names/descriptions and expose them to accessibility APIs. citeturn12search1turn12search3  
Automated tools often check whether interactive controls have an accessible name (from `label`, `aria-label`, `aria-labelledby`, text content for certain elements, etc.). citeturn12search3turn12search8

**Contrast algorithms (colour contrast for text).**  
WCAG contrast is defined using a contrast ratio formula `(L1 + 0.05) / (L2 + 0.05)` based on relative luminance. citeturn11search0  
For enhanced (AAA) contrast, WCAG uses thresholds like 7:1 (normal text) and 4.5:1 (large text), treated as threshold values without rounding. citeturn11search1turn11search9  
axe-core includes rules such as `color-contrast` (AA) and `color-contrast-enhanced` (AAA) that check computed foreground/background contrast against those thresholds. citeturn11search3turn6view0

**Keyboard navigation “simulation”.**  
Pure automated scanners typically do **not** “tab through your app like a user” unless explicitly scripted; instead they check focusability, semantics, and state-dependent properties based on the current DOM. Playwright’s guide explicitly notes that `analyze()` scans the page **in its current state** and you should interact with the UI (open menus/modals) before scanning. citeturn7view0  
In practice: you use Playwright to drive keyboard interactions (e.g., `page.keyboard.press('Tab')`) and run axe scans at meaningful checkpoints, but you still need manual keyboard testing for nuanced focus order, visibility, and trapping behaviours. citeturn7view0turn10view0

### Frames, Shadow DOM, and why “injection” matters

**Injection model.**  
axe-core’s JS must be present in the page under test (and iframes under test) for checks to run; the API documentation notes this explicitly. citeturn2view0  
`@axe-core/playwright` provides a builder API and (per its README) **automatically injects into all frames** to support frame scanning. citeturn1view0

**Cross-origin frames & legacy mode.**  
The Playwright integration includes “legacy mode” to avoid opening an aggregation page; however, legacy mode disables cross-origin frame testing and reports untested frames via the `frame-tested` rule. citeturn1view0turn9search0  
axe-core also documents an `allowedOrigins` configuration, including `<unsafe_all_origins>` which is explicitly “not recommended,” and suggests using a localhost server instead of `file://` when iframe communication is needed. citeturn9search24

**Shadow DOM.**  
axe-core rules are designed to work across open Shadow DOM by using a flattened “virtual” tree; rule development guidance highlights `virtualNode` and the flattened tree as the correct abstraction for hierarchy across shadow boundaries. citeturn16view0  
However, tooling based on axe-core generally cannot inspect **closed** Shadow DOM because it is not accessible to injected JavaScript (documented, for example, in Accessibility Insights for Web FAQ because its automated checks are based on axe-core). citeturn9search15

### First working test (smoke scan) with Playwright Test

Create an accessibility test file (TypeScript example consistent with Playwright docs):

```ts
// tests/a11y/homepage.a11y.spec.ts
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('homepage has no automatically detectable accessibility violations', async ({ page }, testInfo) => {
  await page.goto('https://your-site.example');

  const results = await new AxeBuilder({ page }).analyze();

  // Attach full results for debugging in Playwright HTML report
  await testInfo.attach('axe-results-homepage', {
    body: JSON.stringify(results, null, 2),
    contentType: 'application/json',
  });

  expect(results.violations).toEqual([]);
});
```

This matches Playwright’s documented “scan an entire page” approach and uses `testInfo.attach()` the way Playwright recommends exporting scan results as an attachment. citeturn7view0turn13search1

### Consistent configuration via a reusable fixture

As your test suite grows, use a **fixture** to ensure consistent tags, excludes, and attachment behaviour across tests. Playwright’s accessibility guide shows exactly this pattern by extending the base test with a factory that returns a configured `AxeBuilder`. citeturn7view0

A practical fixture (you will extend it further for WCAG 2.2 + AAA later):

```ts
// tests/fixtures/axe-fixture.ts
import { test as base, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

type AxeFixture = {
  makeAxeBuilder: () => AxeBuilder;
};

export const test = base.extend<AxeFixture>({
  makeAxeBuilder: async ({ page }, use, testInfo) => {
    const makeAxeBuilder = () =>
      new AxeBuilder({ page })
        .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa']); // baseline A+AA

    // Optionally attach in the test itself where you call analyze(), so you can name attachments per scan.
    await use(makeAxeBuilder);
  },
});

export { expect };
```

`withTags()` is the documented way to constrain scans to WCAG-tagged rules. citeturn7view0turn1view0

### Running locally, debugging, and baseline suppression strategies

**Running:** `npx playwright test` is the canonical command for running in CI as well. citeturn8view0

**Stabilise state before scanning:** `AxeBuilder.analyze()` scans the page “in its current state”; open menus/modals and wait for them to render before scanning. citeturn7view0

**Handling known issues:** Playwright documents three common suppression strategies:
- `exclude(selector)` (coarse; excludes descendants),
- `disableRules([ruleId])` (coarse; disables a rule everywhere in that scan),
- “fingerprint snapshotting” of violations to allow a stable baseline without snapshotting the entire verbose object. citeturn7view0

## Configuring WCAG 2.2 tags and AAA rules in axe

This is the “how to achieve this technically” section.

### Understanding tags vs enabled rules

axe-core assigns tags to rules so you can select rule sets by standard and level:
- `wcag2a`, `wcag2aa`, `wcag2aaa`
- `wcag21a`, `wcag21aa`
- `wcag22aa`
- plus per-success-criterion tags like `wcag111` (meaning WCAG SC 1.1.1). citeturn2view0turn5view0

In axe-core, the **default** behaviour of `axe.run()` is to run all enabled rules except experimental. citeturn5view0  
But axe-core explicitly documents that:
- WCAG 2.2 level A & AA rules are **disabled by default** (e.g., `target-size`). citeturn6view0  
- WCAG 2.x level AAA rules are **disabled by default** (e.g., `color-contrast-enhanced`, `identical-links-same-purpose`, `meta-refresh-no-exceptions`). citeturn6view0

So a scan that merely adds tags may still omit those rules unless you explicitly enable them. citeturn6view0turn5view0

### Code example: baseline WCAG A/AA filtering (common starting point)

Playwright’s doc example constrains scans to WCAG A/AA rule tags:

```ts
const results = await new AxeBuilder({ page })
  .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa'])
  .analyze();
```

This is the documented approach for matching the scope of “automated checks” style tools. citeturn7view0

### Code example: include WCAG 2.2 tag and AAA rules (explicit enabling)

Because disabled-by-default rules must be enabled, use `AxeBuilder.options(...)` and provide:
- `runOnly` for tag selection (axe-core mechanism), and
- `rules` to enable the specific rule IDs. citeturn5view0turn1view0turn6view0

```ts
import AxeBuilder from '@axe-core/playwright';

// Recommended: keep the set small and intentional, because some rules are disabled by default.
const results = await new AxeBuilder({ page })
  .options({
    // Select rule groups by tag
    runOnly: {
      type: 'tag',
      values: [
        'wcag2a',
        'wcag2aa',
        'wcag21a',
        'wcag21aa',
        'wcag22aa',   // WCAG 2.2 AA tag exists
        'wcag2aaa',   // AAA tag (WCAG 2.x AAA automated subset)
      ],
    },

    // Explicitly enable disabled-by-default rules you want included
    rules: {
      // WCAG 2.2 AA (documented disabled by default)
      'target-size': { enabled: true },

      // WCAG AAA (documented disabled by default)
      'color-contrast-enhanced': { enabled: true },
      'identical-links-same-purpose': { enabled: true },
      'meta-refresh-no-exceptions': { enabled: true },
    },
  })
  .analyze();
```

Why these rule IDs:
- `target-size` is documented under WCAG 2.2 Level A & AA rules and tagged `wcag22aa` and `wcag258` (mapping to SC 2.5.8). citeturn6view0turn10view0turn2view0  
- The three AAA rules listed above are documented under “WCAG 2.x level AAA rules” and tagged `wcag2aaa` plus their SC tags (e.g., `wcag146`, `wcag249`). citeturn6view0turn2view0  

**Important detail:** `AxeBuilder.options(...)` overrides other builder configuration. The package README states that `.options()` overrides other configured options, including calls to `withRules()` and `withTags()`. citeturn1view0  
That’s why the example above puts **all selection logic into the `options` object** rather than mixing `.withTags()` and `.options()`.

### Code example: custom rule overrides (tightening/relaxing)

You can also override or disable rules via options. axe-core documents disabling rules through the `rules` option. citeturn5view0

Example: disable AA contrast on most pages for performance, but keep AAA contrast enabled only on a small style-representative set (see performance notes later):

```ts
const results = await new AxeBuilder({ page })
  .options({
    runOnly: { type: 'tag', values: ['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa', 'wcag2aaa'] },
    rules: {
      'target-size': { enabled: true },
      'color-contrast': { enabled: false },           // AA contrast off (selectively)
      'color-contrast-enhanced': { enabled: true },   // AAA contrast on (selectively)
    },
  })
  .analyze();
```

This pattern is supported by axe-core’s `rules` options model. citeturn5view0turn6view0

### Code example: selecting by rule IDs instead of tags

For very targeted gates (e.g., “only run WCAG 2.2’s `target-size` + a few AAA rules on PRs”), you can do it by rule IDs:

```ts
const results = await new AxeBuilder({ page })
  .options({
    runOnly: ['target-size', 'color-contrast-enhanced', 'identical-links-same-purpose', 'meta-refresh-no-exceptions'],
    rules: {
      'target-size': { enabled: true },
      'color-contrast-enhanced': { enabled: true },
      'identical-links-same-purpose': { enabled: true },
      'meta-refresh-no-exceptions': { enabled: true },
    },
  })
  .analyze();
```

axe-core’s API docs show `runOnly` can take arrays of rule IDs (or tags). citeturn5view0

## Sample Playwright test snippets: injection, scans, filtering, and failing the build

### Full-page scan + fail on any violation (classic gate)

```ts
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('checkout page is a11y clean (automated)', async ({ page }, testInfo) => {
  await page.goto('https://your-site.example/checkout');

  const results = await new AxeBuilder({ page }).analyze();

  await testInfo.attach('axe-results-checkout', {
    body: JSON.stringify(results, null, 2),
    contentType: 'application/json',
  });

  expect(results.violations).toEqual([]);
});
```

This follows the Playwright guide pattern (scan + assert violations array empty) and uses attachments for report visibility. citeturn7view0turn13search1

### Scan a stateful UI region (menu/modal) after interaction

```ts
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('nav flyout has no a11y violations', async ({ page }) => {
  await page.goto('https://your-site.example');

  await page.getByRole('button', { name: 'Navigation Menu' }).click();
  await page.locator('#navigation-menu-flyout').waitFor(); // ensure rendered

  const results = await new AxeBuilder({ page })
    .include('#navigation-menu-flyout')
    .analyze();

  expect(results.violations).toEqual([]);
});
```

Playwright explicitly recommends interacting to reach the desired state and waiting before scanning. citeturn7view0

### Filter results and fail based on severity (incremental adoption)

In early adoption phases, many teams gate only on serious/critical issues while they burn down legacy defects.

```ts
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('homepage has no serious/critical a11y violations', async ({ page }, testInfo) => {
  await page.goto('https://your-site.example');

  const results = await new AxeBuilder({ page }).analyze();

  const seriousPlus = results.violations.filter(v =>
    v.impact === 'serious' || v.impact === 'critical'
  );

  await testInfo.attach('axe-results-homepage', {
    body: JSON.stringify(results, null, 2),
    contentType: 'application/json',
  });

  // Provide failure context without dumping the full object into the assertion message
  expect(
    seriousPlus.map(v => ({ id: v.id, impact: v.impact, tags: v.tags })),
    'Serious/critical violations found'
  ).toEqual([]);
});
```

The `impact` field and other result object fields are part of axe’s documented results structure. citeturn2view0turn5view0

### Suppress known issues safely (avoid blanket excludes)

Playwright’s docs warn about `exclude()` and `disableRules()` being coarse; the guide suggests a “fingerprint snapshot” approach for more granular baselining. citeturn7view0

```ts
function violationFingerprints(results: any) {
  return results.violations.map((v: any) => ({
    rule: v.id,
    targets: v.nodes.map((n: any) => n.target),
  }));
}

test('known a11y violations have not changed', async ({ page }) => {
  await page.goto('https://your-site.example/legacy');

  const results = await new AxeBuilder({ page }).analyze();

  expect(JSON.stringify(violationFingerprints(results), null, 2)).toMatchSnapshot();
});
```

This mirrors the approach described in the Playwright guide (avoid snapshotting the full violations object). citeturn7view0

## Prototype architecture and schema designs

### Mermaid flowchart (E2E a11y pipeline graph)

```mermaid
flowchart TD
  A[Playwright Test starts] --> B[Launch browser + open page]
  B --> C[Drive UI to target state<br/>(click, type, Tab, open modal)]
  C --> D[Wait for stable UI state<br/>(locators/waitFor)]
  D --> E[Create AxeBuilder with page]
  E --> F[Configure rules/tags<br/>withTags OR options(runOnly+rules)]
  F --> G[Inject axe-core into page + frames]
  G --> H[Run axe.run in browser context]
  H --> I[Collect JSON results<br/>(violations/passes/incomplete/inapplicable)]
  I --> J[Attach results to Playwright report]
  I --> K[Persist JSON/SARIF artifact]
  J --> L{Violations exceed threshold?}
  K --> L
  L -->|Yes| M[Fail test / fail CI quality gate]
  L -->|No| N[Pass]
```

This flow aligns with Playwright’s “analyze in current state” guidance and axe-core’s “run and return JSON results” model. citeturn7view0turn2view0turn5view0

### Component/ER-style schema (store scans, map to WCAG tags)

Below is a prototype ER diagram for storing results across CI builds. It is designed around axe-core’s result structure (rule id, impact, tags, nodes, targets, HTML snippets). citeturn2view0turn5view0

```mermaid

  TEST_CASE_RUN {

  }

  AXE_SCAN {
    string scan_id
    string test_run_id

  }

  AXE_VIOLATION {
```

## Example JSON report format and WCAG 2.2/AAA mapping

### What axe results look like (shape and fields)

axe returns a results object containing arrays like `passes`, `violations`, `incomplete`, `inapplicable`. The documentation explains the meaning of these arrays and key fields like `id`, `impact`, `tags`, `nodes`, `html`, and `helpUrl`. citeturn2view0turn5view0

A concise example (illustrative, not copied from a specific run):

```json
{
  "url": "https://your-site.example/home",
  "timestamp": "2026-03-30T10:15:22.123Z",
  "testEngine": { "name": "axe-core", "version": "4.x" },
  "testEnvironment": { "userAgent": "Mozilla/5.0 ..." },
  "violations": [
    {
      "id": "target-size",
      "impact": "serious",
      "tags": ["cat.sensory-and-visual-cues", "wcag22aa", "wcag258"],
      "help": "Ensure touch targets have sufficient size and space",
      "helpUrl": "https://dequeuniversity.com/rules/axe/4.x/target-size?application=axeAPI",
      "nodes": [
        {
          "target": [["#checkout-form", "button.place-order"]],
          "html": "<button class=\"place-order\">Place order</button>",
          "failureSummary": "Fix any of the following: Target size is too small ..."
        }
      ]
    },
    {
      "id": "color-contrast-enhanced",
      "impact": "serious",
      "tags": ["cat.color", "wcag2aaa", "wcag146"],
      "help": "Ensure contrast meets WCAG 2 AAA thresholds",
      "helpUrl": "https://dequeuniversity.com/rules/axe/4.x/color-contrast-enhanced?application=axeAPI",
      "nodes": [
        {
          "target": ["#promo-banner .fine-print"],
          "html": "<span class=\"fine-print\">Terms apply</span>",
          "failureSummary": "Fix any of the following: Insufficient contrast ..."
        }
      ]
    }
  ],
  "incomplete": [],
  "passes": [],
  "inapplicable": []
}
```

### Mapping logic to WCAG 2.2 and AAA

A robust mapping approach is:

1) For each violation, inspect `tags`.  
2) Classify it into buckets:
   - WCAG 2.2 AA if `tags` contains `wcag22aa`  
   - WCAG AAA if `tags` contains `wcag2aaa`  
3) Extract SC identifiers from `wcag***` tags (like `wcag258` → SC 2.5.8) using axe’s documented convention that `wcag111` maps to SC 1.1.1. citeturn2view0turn6view0turn10view0

Concrete examples backed by axe-core’s own rule listings:
- `target-size` is tagged `wcag22aa` and `wcag258`. citeturn6view0turn10view0  
- `color-contrast-enhanced` is tagged `wcag2aaa` and `wcag146`. citeturn6view0turn11search9  

## Limitations, recommended manual checks, best practices, performance, and security/privacy

### Limitations of automated accessibility scanning

Automated checks are valuable, but both Playwright and axe-core documentation emphasise limitations:

- Automated tests catch common issues (labels, contrast, duplicate IDs), but **many issues require manual testing**; Playwright explicitly recommends combining automation with manual assessments and inclusive user testing. citeturn7view0  
- axe does not test **hidden/inactive regions** (like inactive menus/modals) unless you reveal them and run analysis again. citeturn2view0turn7view0  
- Some results are **incomplete/needs review**, reflecting limits of determinism and technical constraints. citeturn16view0turn2view0  
- Shadow DOM limitations apply: open Shadow DOM is supported by axe-based tooling, but **closed Shadow DOM cannot be fully tested** by injected JS. citeturn9search15turn16view0  
- Frame testing has constraints: legacy/compat modes can disable cross-origin frame checks; axe-core has explicit allowed-origins controls, including an `<unsafe_all_origins>` option that is not recommended. citeturn1view0turn9search24  

### Recommended manual checks to pair with your E2E automation

If your goal is “WCAG 2.2 + AAA mindset,” manual checks should focus on areas that are difficult to automate reliably and areas where conformance depends on user experience quality, not just markup correctness.

High-value manual checks (pragmatic, flow-based):

- **Keyboard-only end-to-end flows**: can you complete key journeys without a mouse; is focus always visible; no keyboard traps; logical focus order. WCAG’s operable principle and focus-related SCs (including new 2.2 focus criteria) make this essential. citeturn10view0  
- **Screen reader navigation** (at least one platform+SR combo): confirm names/roles/states announced match intent; confirm dynamic updates (errors/status) announced appropriately (often partially automatable, frequently requires human validation). citeturn12search0turn12search1turn12search17  
- **Zoom/reflow/responsive**: at 200–400% zoom, does layout remain usable and readable; does content reflow sensibly. (WCAG 2.2 extends prior guidance and is designed to be applicable across devices). citeturn10view0  
- **Cognitive & content clarity**: error messages, instructions, authentication usability, and consistency checks are often not fully automatable at the “is this understandable” level. citeturn10view0  

A practical workflow is: run automated scans on every PR; run manual audits on a cadence (release trains) and when major UI patterns change, using a structured manual toolset (Playwright points to Accessibility Insights for Web for guided WCAG coverage). citeturn7view0

### Best practices for integrating into engineering workflows

**Adopt in layers.**  
Start with high-signal automated scope (WCAG A/AA tags), then progressively enable stricter rules (WCAG 2.2 AA automated subset + AAA automated subset), then expand state coverage (modals, menus, wizards). This fits with how Playwright describes scanning page state and how axe documents tags and enabled rules. citeturn7view0turn2view0turn6view0

**Use fixtures to enforce consistency.**  
Centralise your `AxeBuilder` configuration in fixtures so you don’t drift across files. Playwright explicitly demonstrates this. citeturn7view0

**Treat suppressions as technical debt with visibility.**  
Prefer violation fingerprint snapshots over broad excludes; Playwright warns about the downsides of `exclude()` and `disableRules()`. citeturn7view0

**Make results developer-actionable.**  
Always attach full JSON to the Playwright report (`testInfo.attach`) so engineers can see details without rerunning locally. The attachment API supports `application/json`. citeturn7view0turn13search1  
Optionally export SARIF and publish it in CI systems that can visualise it (Microsoft’s sample demonstrates SARIF conversion and publication in Azure Pipelines). citeturn15view0turn19view0

### Performance considerations (keep scans fast enough for PR gating)

axe-core documents several known performance characteristics and mitigation strategies:

- Very large pages (e.g., >50K elements) can cause analysis times >10s on reasonable CPUs. citeturn2view0  
- Reduce computation by restricting result types (e.g., focusing on `violations`). citeturn2view0  
- Colour-contrast analysis can be expensive; analyse a representative subset of pages for contrast rather than every page when many pages share styles. citeturn2view0turn11search3  

In Playwright-level terms, you also control performance by:
- scanning only critical flows/pages per PR,
- using `include()` for component-level scans where practical,
- running heavier “full site sweep” scans nightly instead of on every PR. citeturn7view0turn1view0

### Security and privacy concerns in test artefacts

Key risks and mitigations:

- **Scan artefacts may include HTML snippets and selectors**, which can inadvertently contain personal data if you run tests against production-like datasets. Axe results include fields like `html` snippets and `target` selectors per node. citeturn2view0turn5view0  
  Mitigation: run E2E a11y tests in environments with synthetic data; scrub attachments before long-term retention; restrict artefact access.

- **Cross-origin frame testing configuration can be risky**. axe-core documents `<unsafe_all_origins>` as “not recommended.” citeturn9search24  
  Mitigation: prefer same-origin test environments; avoid broad origin allowances; treat any relaxation as a reviewed exception.

- **Legacy mode trade-offs**. The Playwright integration’s legacy mode can reduce issues in restricted environments but disables cross-origin frame testing. citeturn1view0turn9search0  
  Mitigation: use legacy mode only when necessary; rely on `frame-tested` results to detect untested frames and add targeted strategies.
